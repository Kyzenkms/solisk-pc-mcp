Security / Trust boundaries

Assume every permission matters.

PC Control MCP deliberately exposes powerful local capabilities. Security depends on authenticated clients, least-privilege scopes, local approval, and keeping credentials out of untrusted contexts.

Security model

The AI client sends authenticated MCP requests to either the local runtime or relay. The relay authorizes the credential and forwards approved traffic to the connected desktop. Tool execution occurs on the PC.

Boundary Purpose
Owner key Controls device ownership and high-privilege administration.
Scoped key Limits a client to selected tool categories.
Approval mode Requires local user confirmation before execution when enabled.
Allowed paths Restricts filesystem operations to configured directories.
Relay room Maps a unique device identity to its active desktop socket.

Credentials

Use a different scoped key for each client or person. Do not share the owner key. Hosted and current self-hosted relay implementations store registered API keys using salted scrypt hashes rather than plaintext records.

Regenerating the MCP URL stops the previous runtime connection, removes the old relay room, revokes related relay tokens, and creates a new device identity. Clients must be updated manually.

Transport

The managed endpoint uses HTTPS and secure WebSockets. Local-only HTTP is bound to loopback. Self-hosted operators are responsible for valid TLS, DNS, firewall rules, updates, and proxy configuration.

TLS protects network transport. Current beta does not provide application-level end-to-end encryption between MCP client and desktop beyond the relay transport channel.

Storage

Desktop configuration and credentials are stored under the current Windows user profile. Relay room and OAuth state are stored on the relay host. Self-hosted deployments persist state in Docker volumes.

Back up configuration securely. Never commit config.json, rooms.json, OAuth token files, or generated secrets.

Current beta limitations

  • Windows installer is unsigned and may trigger SmartScreen.
  • Desktop TLS verification and Electron CSP require final release hardening.
  • No application-level end-to-end encryption across the managed relay.
  • Powerful tools can cause data loss or system changes when authorized.
  • AI prompt injection can influence connected clients; scopes and approval remain necessary.

Report a vulnerability

Do not open a public issue for sensitive vulnerabilities. Use a private GitHub security advisory or email kyzenkms@duck.com.

Include affected version, reproduction steps, impact, and a safe proof of concept. Do not include live API keys, private files, or unrelated user data. Reports are acknowledged within 72 hours when possible.
